- **上位の正体**: 1〜3位は同じ「向きの木」の枝。9/29 20:06〜10/1 13:52 の枚数の推移が0.01枚単位まで一致した（実データ、逆算・検算済み）。
- **上位の「向き」は判断ではなく生き残った枝**: 首位の鍵は上げで買いの枝、下げで売りの枝に入れ替わっていた。真似るべきは向きではなく、木の作り（区切る時刻・深さ・費用）。

## Q7 汎用的な戦略思想

原則は5つ。この大会で実データで確かめたのは原則1・3・4で、他の市場への持ち出しはすべて要検証。各原則に、根拠・区分・前提・持ち出せる範囲・反証の方法を付けた。

### 原則1 区切りの回数は、値動きの大きい時間帯に集中させる

- **根拠**: 9/28 夜、上位は1〜2時間おきに区切って約560点伸ばした。こちらは予定表で1回だけで、差が約560点開いた（Q5・Q6）。
- **区分**: この大会では実データで確認。一般化は推論（要検証）。
- **前提**: 木の深さ（鍵の数＝2の区切り回数乗）に上限がある。値動きの大きさが時間帯で偏る（米国市場の時間帯など）。
- **持ち出せる範囲**: 回数や予算に上限がある判断全般（売買の回数、注文の上限、API の呼び出し回数）。値動きが時間帯で偏らない市場では効果が小さい。
- **反証の方法**: 次の大会で、区切りを時間帯で均等に配る木と、値動きに応じて配る木を並べて走らせ、最良の枝の点数を比べる。

### 原則2 区切りの回数には上限があるので、向き替えの費用を超える反転が起きやすい時刻に使う

- **根拠**: 1回の向き替えの費用は 110〜142点で、47枚では 1.0〜1.3% の値動きに相当（Q3）。区切っても「そのまま持つ枝」が残るので、区切ったことで最良の枝が損をすることはない（コードの作りから）。費用は、区切るかどうかではなく、限られた回数をどこに使うかの基準になる。
- **区分**: 費用の大きさは実データ。判断の基準としては推論（要検証）。
- **前提**: 手数料が建玉の額に比例し、終値との差で手数料が増える決まりがある。
- **持ち出せる範囲**: 手数料やスプレッドのある市場すべて。費用は市場ごとに測り直す。
- **反証の方法**: 費用相当（約1.1%）を超える反転が起きた時刻と、区切った時刻がどれだけ重なっていたかを、上位とこちらで比べる。

### 原則3 上位に出る鍵は判断の結果ではなく、生き残った枝

- **根拠**: 首位の鍵は、上げで買いの枝、下げで売りの枝に入れ替わっていた。1〜3位は同じ木の枝だった（Q1・Q2・Q5）。
- **区分**: 実データで確認。
- **前提**: 1人が何本でも鍵を持てる。順位が最良の1本で決まる。
- **持ち出せる範囲**: 多数の候補を並べて最良だけを数える大会や評価（エアドロップの抽選、コンテスト）。実際の資金運用では、全部の枝の損益が自分に返るため成り立たない。
- **反証の方法**: 上位の「向き」の当たり外れが、相場の予測で説明できるかを調べる（向き替えの前後の値動きに偏りがあるか）。

### 原則4 点数が積み上がる勝負では、序盤の取りこぼしが最後まで残る

- **根拠**: 9/29 05:10 に約470点あった差は、その後3日半ほぼ一定（約490〜630点）だった（Q6）。
- **区分**: この大会では実データで確認。一般化は推論（要検証）。
- **前提**: 枚数に上限があり、後から取り返す速さが相手と同じ。
- **持ち出せる範囲**: 期間内の累計で順位が決まるもの全般。
- **反証の方法**: 次の大会で、開始直後から値動きに応じて区切る設定にし、序盤の差が縮むかを見る。

### 原則5 安全のための余裕は、失敗の確率と取り分の減り方の両方で決める

- **根拠**: こちらは、売りの1枚に参照価格の約1.047倍を用意していた（ルールの最低ラインは約1.023倍）。そのぶん枚数が約2.3%少なかった（Q4）。
- **区分**: 枚数の差は実データ。余裕を削った場合に失敗がどれだけ増えるかは未確認。
- **前提**: 担保が足りないと取引が不成立（void）になる。
- **持ち出せる範囲**: 担保や証拠金のある取引全般。
- **反証の方法**: 過去の約定で、手数料が1%を超えた割合と超えた幅を数え、余裕を最小限にしても不成立にならなかったかを確かめる。

## Q8 汎用的な設計

運用の障害5件は、どれも「動いているように見えて、実は止まっていた」型だった。合計の停止時間は約36時間。ここから設計の原則を5つ導いた。障害そのものは実データで、原則の効き目は次回の運用で確かめる（要検証）。

| 時刻（JST） | 起きたこと | 原因 | 対策 |
| --- | --- | --- | --- |
| 10/2 19:55〜10/3 08:33 | 監視プログラムが12時間半停止 | 監視を起こす側のプロセス検索が tmux 本体の起動コマンドに一致し、動いていると誤認 | 検索を python 本体に限定 |
| 10/1 20:30〜10/2 19:47 | 取引プログラムの1つがパスフレーズ待ちで23時間停止 | 再起動の後に、記録が進んだかを確かめなかった | 記録が進まない時の通知を追加 |

### 原則A 「動いているか」は、プロセスではなく記録の進みで判定する

- 根拠: 23時間停止の件。プロセスは生きていたが入力待ちだった。
- 持ち出せる範囲: bot・常駐プログラム全般。完了の判定も同じ（「コマンドが通った」ではなく「記録の時刻が進んだ」）。
- 反証の方法: 記録の鮮度で判定する健康診断の運用中に、停止の見逃しが起きるかを数える。

### 原則B 監視そのものが止まったことが、外から分かるようにする

- 根拠: 監視の12時間半停止。止まった監視は自分の停止を知らせない。
- 持ち出せる範囲: 監視・通知の仕組み全般。外から見える心拍（公開ページの更新時刻など）を別経路で見る。
- 反証の方法: 監視を意図的に止め、何分で気づけるかを測る。

### 原則C 依存先が止まる・遅れる・誤一致する時の動きを、変更のたびに1行ずつ書く

- 根拠: 審判の停止で保活が止まった件、プロセス検索の誤一致の件。
- 持ち出せる範囲: 外部 API・他プロセスに頼るもの全般。
- 反証の方法: 変更記録に依存先の行があった変更と、なかった変更で、障害の起きる割合を比べる。

### 原則D 常駐はログインのセッションから切り離す

- 根拠: SSH の切断で tmux ごと止まった件（原因は推定）。
- 持ち出せる範囲: VM 上の常駐プログラム全般（systemd、cron、Linger の設定）。
- 反証の方法: SSH を切った状態で一晩動かし、止まらないかを確かめる。

### 原則E 判断に使う指標は、採点と同じ計算に合わせる

- 根拠: mark で数えた並びで「上位が固まった」と誤判断した件。
- 持ち出せる範囲: 評価や順位が絡む判断全般（自前の指標を、公式の採点方法に合わせて検算する）。
- 反証の方法: 自前の指標と公式の点数を毎回突き合わせ、ずれた回数を数える。
